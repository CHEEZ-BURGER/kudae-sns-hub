# Cloudflare R2 연결과 기존 배포 3개 이전

## 현재 상태 (2026-10-06)

R2 인증/CORS, 서버 연결과 함수 배포, 기존 배포 3개의 실제 복사 및 DB 전환을
완료했습니다. 원본 77개와 썸네일을 합친 154개 객체, 총 191,481,020바이트를
크기/메타데이터/재다운로드 SHA-256으로 확인했습니다. Standard 비공개 버킷입니다.
제목/본문/크레딧/순서/크기/비율/기존 공유 링크/만료일이 유지됨을 전후 비교했고,
세 공개 배포의 원본과 썸네일이 R2에서 직접 내려오는 것을 확인했습니다.
사용자가 설치된 확장 2.2.2에서 이미지 두 개가 정상 입력된 것을 확인했습니다.
Pages 빌드도 R2 신규 업로드를 사용하도록 지정했으며 배포 결과는 Actions에서 확인합니다.
Supabase 원본은 복구용으로 남겨뒀습니다. 기존 확장 소스/버전은 변경하지 않았습니다.

유닛 테스트 65개, 기본/R2 빌드, 서버와 이전 스크립트 타입 검사를 통과했습니다.
실제 DB 롤백 검사로 R2 파일 추가/보존/영상 교체/삭제 및 이전 충돌/권한 거절을 확인했습니다.
영상의 실제 SNS 업로드, 모든 플랫폼 및 모바일 기기 실기 검증까지 완료한 것은 아닙니다.

R2는 무조건 무료인 요금제가 아닙니다. Standard의 포함량은 월 10GB-month,
Class A 100만 회, Class B 1,000만 회이며 인터넷 전송료는 없습니다.
포함량 초과, 별도 유료 서비스, 정책 변경 등으로 요금이 발생할 수 있습니다.
계정 전체 사용량을 Cloudflare 대시보드에서 확인하세요.
예산 알림은 서비스 차단이나 지출 상한이 아닙니다.

## 구조

- GitHub Pages: 기존 웹앱 및 공유 미리보기 그대로.
- Supabase: 기존 Auth/DB, 관리자 권한 확인, 접근 가능한 파일 URL 발급.
- R2: 비공개 이미지/영상 원본 및 썸네일. 변환 없이 원본 보존.
- 외부 경로 `r2:`와 기존 Supabase 경로를 같이 읽습니다. `s3:` AWS도 유지합니다.
- R2 파일은 15분 유효한 S3 API 서명 GET URL로 직접 전달합니다.
  공개 버킷/Workers 유료 플랜/사용자 도메인을 추가로 만들지 않습니다.
- 기존 확장이 허용한 Supabase 호스트에서 HTTP 302만 반환하여 R2로 연결합니다.
  파일 바이트는 Supabase가 중계하지 않습니다. CORS를 설정하더라도 기존 확장
  v2.2.2의 실제 원본 전달 검증이 필요합니다. 검증 전에는 DB를 바꾸지 않습니다.

## 직접 설정해야 하는 항목

현재 자동 브라우저 접근은 저장된 차단 상태와 허용 설정의 불일치로 막혔습니다.
이를 우회하여 콘솔을 조작하지 않습니다. 계정 설정은 사용자가 직접 진행하고,
CLI 작업에는 사용자가 의도적으로 제공한 해당 서비스 키만 사용합니다.

1. 버킷 Settings → CORS Policy에 `infra/r2/cors.json`을 적용합니다.
   PUT은 Pages origin만, GET/HEAD는 기존 확장의 리디렉션을 위해 모든 origin에
   허용합니다. CORS 허용은 인증 허용이 아닙니다. 모든 파일은 서명 URL이 필요합니다.
2. R2 API 키는 **해당 버킷만**, Object Read & Write 권한으로 생성합니다.
   계정 관리자 전체 권한 키를 만들지 않습니다. 생성은 사용자가 직접 수행합니다.
3. 비밀 키는 채팅/소스/프런트 환경변수에 넣지 않습니다.
   `infra/r2/secrets.env.example`은 이름과 예시만 제공합니다.
   로컬 이전용 실제 값은 `.env.r2-migration.local`에 입력하고 Git 제외를 확인합니다.
   서버용 키는 해당 Supabase 프로젝트의 Edge Functions Secrets에 등록합니다.
4. 서버 Secrets: `SNS_MEDIA_BACKEND=r2`, `SNS_R2_ACCOUNT_ID`, `SNS_R2_BUCKET`,
   `SNS_R2_ACCESS_KEY_ID`, `SNS_R2_SECRET_ACCESS_KEY`.
   Supabase 서비스 키는 이전 스크립트만 필요합니다. 기본 서버 환경에는 이미 있습니다.

## 서버 적용 순서

1. 기존 `20261006000000_atomic_media_edit.sql`에 이어
   `20261006010000_r2_media_edit.sql`과 `20261006020000_switch_media_storage.sql` 적용.
2. `media-admin`, `media-redirect`, `public-distribution` 배포.
   JWT gateway 설정은 `supabase/config.toml`을 따릅니다. 서버는 자체 관리자/JWT/HMAC를 검사합니다.
3. 아직 `VITE_MEDIA_BACKEND=supabase`를 유지합니다. 기존 파일과 링크를 먼저 확인합니다.
4. 별도 테스트 배포로 이미지와 영상, 파일 크기와 비율, CORS, 개별 다운로드,
   데스크톱 및 모바일, 기존 설치 확장 2.2.2에서 원본 넣기를 검증합니다.
   테스트 데이터를 자동으로 기존 배포에 삽입하지 않습니다.

## 기존 세 배포 이전 스크립트

`scripts/r2-migration.ts`는 기본 실행으로 원본을 복사하거나 DB를 수정하지 않습니다.
작업 디렉터리는 저장소 루트입니다. 테스트/소스 점검과 실제 이전은 구분합니다.

```powershell
npx deno run --node-modules-dir=none --no-lock --env-file=.env.r2-migration.local --allow-env --allow-sys --allow-net --allow-read=work/r2-migration --allow-write=work/r2-migration scripts/r2-migration.ts --plan
```

- 해당 Supabase 프로젝트 및 버킷 이름을 고정 검증합니다.
- 게시된 배포가 정확히 세 개가 아니면 중단하고 대상을 확인합니다.
- 계획은 배포 제목, ID, 파일 수와 원본 총 크기를 출력합니다. 키/토큰은 출력하지 않습니다.
- 확인 후 마지막 인자를 `--copy`로 바꿉니다.
- 각 파일은 Supabase에서 한 번 내려받아 R2에 변환 없이 업로드합니다.
  이 최초 다운로드는 Supabase egress를 사용합니다.
- 원본 크기를 기존 DB와 비교하고, R2 HEAD 메타데이터 및 재다운로드 SHA-256을
  모두 확인합니다. ETag만으로 원본 동일성을 판단하지 않습니다.
- `work/r2-migration/verified-manifest.json`에는 기존 경로, DB 버전, 공유 토큰과
  복사 파일 체크섬이 포함됩니다. 이 비공개 보고서는 Git 제외하며 공유하지 않습니다.
- 중단 뒤 `--copy` 재실행은 검증 완료된 객체를 확인하여 이어갑니다.
  Supabase 파일은 자동 삭제하지 않으며 DB도 이 단계에서는 수정하지 않습니다.
- 원본 예상 7GB 또는 대상 버킷 8GB를 넘으면 보수적으로 중단합니다.
  이전 중 다른 도구가 업로드하지 않도록 하세요. 이 제한은 계정 전체 과금 차단이 아닙니다.

모든 복사, 실사용 확장 및 서버 검증을 마친 뒤에만
`R2_COMPATIBILITY_VERIFIED=yes`를 이전 환경에 설정하고 `--commit`을 실행합니다.
확인 없이 이 설정을 넣어 검증 절차를 건너뛰지 않습니다.

- 세 배포의 최신 수정 시각과 모든 파일 경로를 비교하여 충돌 시 전체를 거절합니다.
- 세 배포의 경로는 **하나의 DB 트랜잭션**으로 전환합니다.
- 공유 토큰, 제목/본문/크레딧, 순서, 파일명, 만료 시각을 바꾸지 않습니다.
- 실패 시 보고서를 지우고 처음부터 재실행하지 말고 DB와 저장소 상태를 확인합니다.
- 전환 후 실제 배포 페이지와 기존 확장을 다시 확인합니다.

## 연결/실기 검증 도구

`scripts/r2-connection-check.ts`는 버킷 목록과 서명 URL의 OPTIONS만 확인합니다.
실제 파일을 만들거나 다운로드하지 않으며 키/서명 URL을 출력하지 않습니다.

`scripts/r2-compatibility-check.ts`의 `--prepare`는 이미 검증된 원본 두 개를
참조하는 별도 임시 배포를 만듭니다. 실제 배포나 원본 파일은 수정하지 않습니다.
테스트 배포의 생성 시각은 2000년으로 두어 보관 개수 정리 시 실제 배포보다 먼저
정리되도록 하며, 유효기간은 6시간입니다. 보고서는 `work/r2-migration`에만 둡니다.
`--check`는 공개 API/CORS, Supabase의 바이트 없는 302, R2 원본 크기/SHA-256,
익명 관리자 접근 거절을 확인합니다. Chrome 확장 실기 검증을 대신하지 않습니다.
사용자가 기존 설치 확장으로 두 이미지를 작성창에 넣어 확인한 뒤 `--cleanup`으로
오직 임시 배포만 삭제합니다. R2와 Supabase 원본은 삭제하지 않습니다.

`supabase/tests/r2-switch-regression.sql`은 실제 DB에서 트랜잭션을 롤백하면서
잘못된 대상 개수/수정 버전/파일 경로 거절과 기존 메타데이터 보존, 함수 권한을 확인합니다.
Supabase에서 R2로 전환하기 전에 실행합니다.
`supabase/tests/r2-media-edit-regression.sql`은 별도 임시 배포를 트랜잭션 안에서만
만들어 R2 원본 보존, 파일 추가, 영상 교체와 삭제 경로 반환을 검사한 뒤 롤백합니다.
실제 저장소 파일이나 관리자 계정은 생성하지 않습니다.
`scripts/r2-distribution-check.ts`는 비공개 전후 원고 스냅샷과 공개 링크/파일을 비교합니다.

## 신규 업로드 활성화와 Pages

검증 후 `.github/workflows/deploy-pages.yml`의 빌드 환경 `VITE_MEDIA_BACKEND=r2`로
Pages를 빌드/배포합니다. 로컬 환경에서 값이 없으면 기존 `supabase`입니다.
클라이언트와 서버 저장소 선택이 다르면
업로드를 중단하고 새로고침을 안내합니다. 서버는 업로드 후 실제 객체 크기/형식도 확인합니다.
기존 확장 소스와 버전을 변경하지 않습니다.

## 보존과 롤백

Supabase 원본은 사용자가 별도 정리를 승인하고 모든 링크를 확인할 때까지 보존합니다.
R2로 옮겨도 이미 쓴 이번 기간 Supabase 전송량이 차감되지는 않습니다.
신규 업로드를 `supabase`로 돌려도 R2에 있는 파일은 R2 함수와 키가 있어야 읽을 수 있습니다.
DB 롤백에는 비공개 보고서의 기존 경로를 사용하고 새 편집 내용을 덮어쓰지 않도록
현재 버전과 비교합니다. 직접 SQL로 무조건 덮어쓰지 않습니다.
